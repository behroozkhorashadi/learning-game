Adaptive Learning Games · architecture

Learning Game Architecture

Two levels. The system view shows what runs where and how requests flow. The code views break the FastAPI backend and the React frontend into their layers.

Level 1

System

A React SPA in the kid's browser talks to one FastAPI process through the Vite proxy. All state lives in a local SQLite file; OpenAI is the only external call, used for story illustrations and profile-photo remixes. Adaptive difficulty is decided server-side. The backend's OpenAPI schema generates the frontend's API types, and make preflight (run again by CI) enforces the architecture below.

Level 2 · backend

Backend code (FastAPI, Python 3.12)

Routes in app/main.py call services for IO and orchestration. The Loop A engine is pure functions with no DB access; loop_a_service wraps it with persistence and the append-only event log. Games plug in through the GameModule contract and self-register in the registry. New-style features (app/todo/ is the example) are built from factories and wired only in app/composition/, which app/main.py calls to mount their routers. Legacy modules migrate into that shape one at a time (backend/MIGRATION.md).

Level 2 · frontend

Frontend code (React 19, Vite, Three.js)

App.tsx routes between screens with component state, not a router library. Legacy screens fetch /api directly, and game rules live in pure modules under src/lib. Migrated code lives in feature folders whose filenames carry their layer: screens are bound with injected capabilities, reach the server through src/api/ adapters (zod-parsed, typed from the backend's OpenAPI schema) and useQuery, and are assembled once. Legacy may import new-style code, never the reverse (MIGRATION.md).
