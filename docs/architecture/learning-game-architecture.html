Adaptive Learning Games · architecture

Learning Game Architecture

Two levels. The system view shows what runs where and how requests flow. The code views break the FastAPI backend and the React frontend into their layers.

Level 1

System

A React SPA in the kid's browser talks to one FastAPI process through the Vite proxy. All state lives in a local SQLite file; OpenAI is the only external call, used for story illustrations and profile-photo remixes. Adaptive difficulty is decided server-side. The backend's OpenAPI schema generates the frontend's API types, and make preflight (run again by CI) enforces the architecture below.

Level 2 · backend

Backend code (FastAPI, Python 3.12)

Every route group is a feature folder under app/ (app/todo/ is the worked example): pure schemas and rules, effect repositories, clients, services and routes built by factories, and wired only in app/composition/. Features never import each other; assembly passes each one what it needs from the others (a profile lookup, the event log, badge awarding). app/main.py is just the uvicorn entry. The Loop A engine and the game item generators are pure; the play service runs them over storage and the append-only event log.

Level 2 · frontend

Frontend code (React 19, Vite, Three.js)

Every file lives in a feature folder and carries its layer in its name. src/main/ is the shell: one navigation value routes between screens (no router library), and every screen is bound with injected capabilities and assembled once at startup. Screens reach the server through src/api/ adapters (zod-parsed, typed from the backend's OpenAPI schema) and useQuery; browser globals are named only in *.assembly.* files. Game rules are pure libraries inside their features.
